## Finding

The candidate contains an actual, optional, in-process ML-DSA-65 signing/verifying adapter and real provider preparation. It does **not** migrate any native ledger, Node, DA, task-kernel, service-settlement, research-command or Hepta-handoff authorization owner to PQ. Searching the tracked Rust sources for `PqNative`, `PqSignatureObservation`, `pq_auth::` and `preflight_unverified_with_spki` finds the primitive/parser, their documentation, and tests; there is no consumption of the cryptographic observation by an application authority owner. This is a directly observed integration gap, not a failure of ML-DSA itself.

The useful package-3 completion claim is therefore “native TPQ1 parser + actual in-process ML-DSA-65 adapter + provider preparation and negative controls.” “All owner migration”, “Chain/Hepta authorization is PQ” and “whole-chain quantum security” remain unqualified. Nothing in this review changes pure PoN, introduces a permissioned fork choice, or treats signatures as mining work.

## What the new adapter actually establishes

Source: `trillionnium/crates/trnm-crypto-primitives/src/pq_auth.rs`.

- Lines 55–60 require OpenSSL 3.5 or later. The CI preparation pins a specific 3.5.9 archive; the library runtime guard itself is a minimum version check, not an exact binary provenance guarantee.
- Lines 71–84 define a privately constructed borrowed `PqSignatureObservation`. It has no `Deserialize`, public field constructor, or `Clone`; its getters expose the authenticated statement and signer key ID. This is cryptographic evidence, not a state-transition capability.
- Lines 95–112 bind a strict DER SPKI to an independently supplied key-ID pin, decode it through OpenSSL, require `ML_DSA_65`, and require an exact DER round trip.
- Lines 115–132 perform TPQ context preflight and a real in-process EVP `verify_oneshot` call. An application cannot obtain the observation merely by passing a CLI success status or a caller-controlled verification Boolean. There is no classical fallback in this adapter.
- Lines 143–183 accept an already owned private PKey, sign the exact 176-byte statement, require the exact 3,309-byte signature length, and self-verify the produced signature. This does not implement durable key custody, a signer policy, an HSM, or automatic key generation.
- A second valid verification of the same frame is intentionally possible. No durable nonce is consumed by this primitive. The future application owner must check registered role, current key generation, sequence and revocation, and atomically record the authorized effect.

`trnm-crypto-primitives/Cargo.toml:19` exposes this through `pq-native-openssl = ["dep:openssl"]`; it is optional and off by default. `src/lib.rs:225–226` feature-gates the module.

Source: `trillionnium/crates/trnm-protocol/src/pq_frame.rs`.

TPQ1 has a 176-byte unsigned statement, 3,309-byte ML-DSA-65 signature, 2-byte signature length, and thus 3,487 signed bytes. Public key material is 1,952 bytes and canonical DER SPKI is 1,974 bytes. `PqFrameExpectation` binds purpose, network, owner context, key ID, generation, sequence, expiry, current time and payload. The payload commitment is SHA-384 with domain separation and an explicit byte length; maximum payload is 64 MiB. `ml_dsa_65_key_id_from_spki` checks exact DER framing and hashes the SPKI to a SHA-256 identity; it is not a substitute for the actual provider verification. `preflight_unverified_with_spki` remains explicitly unverified syntax/context checking.

The expectations must originate from independently authenticated application state. Copying all expected fields from an attacker-supplied frame would nullify the application-level binding even if the signature mathematics were correct. The six permitted purpose byte values are not, by themselves, a complete typed authorization policy for all native owners below.

## Abstract interfaces and absences that should not be misreported

- `trnm-release-bundle/src/lib.rs:323` defines an abstract `verify_release_signature` trait and `:415` consumes it. The only concrete implementation located at `:515–517` is the `AcceptSignature` **test** implementation. This is neither evidence of a real production Ed25519 release backend nor evidence of PQ release provenance. A real deployment backend and its key custody/authorization still need qualification.
- `trnm-mempool/src/typed_admission.rs:393–403,582,656` defines and consumes caller-owned `SignedAdmissionHooks::verify_signature`; its durable pending-nonce authority is a separate boundary. This generic hook is not an additional cryptographic implementation. The actual Node M05 implementation is included in the table.
- `trnm-types/src/relay/verifier.rs:152,221` (and the retained parallel code in `relay.rs:351,450`) accepts a caller signature-verifier callback. That extension point does not demonstrate a wired PQ authority owner.
- `trnm-transport/src/lib.rs:195,371` delegates frame verification through `FrameVerificationSourceV0`. The crate's header explicitly says it owns no socket/TLS transport. There is no newly integrated PQ KEM/encrypted-session owner in the paths inspected. `trnm-pon-node/src/ingress.rs:1331` explicitly limits the transport claim to integrity and excludes confidentiality. Do not invent an observed X25519/TLS backend; the issue here is missing confidentiality/KEM qualification, not a demonstrated legacy X25519 implementation.
- Checkpoint CAS/Merkle hashes, OS filesystem permissions and unsigned internal capabilities are separate boundaries. Their existence does not mean every type needs an ML-DSA signature; their upstream authorization and any cryptographic binding assumptions must instead be included in the migration model.
- The old signer-journal crate was retired; it must not be reported as a live production owner. The current operator and task/state owners above are the relevant migration locations.

## Required gates before calling native authority migration complete

1. **Fresh canonical versions.** Define a PQ transaction/transport/certificate profile with algorithm identity, exact field widths, key-ID lookup, size ceilings and domain separation. TPQ1's 3,487 bytes do not fit the 2,048-byte PNX cap, and ML-DSA public keys cannot replace a 32-byte Ed25519 key in place. Define the new database/account/authority representations and migration of stored objects, not just the signature function.
2. **A trustworthy initial PQ registry.** Register PQ keys through an authenticated activation or fresh trust anchor. An attacker who can already forge an old Ed25519 owner can forge a classical “rotate to my PQ key” instruction; that bridge is not retroactively quantum secure. Explicitly state the pre-quantum trust assumption, genesis/activation boundary, fallback policy and treatment of obsolete signatures.
3. **Actual state-owner consumption.** Each owner must derive the expected purpose, network, owner context, current key ID/generation, sequence and expiry from trusted state, perform real PQ verification, and atomically consume the authorized operation. Preserve all native role, fee, policy, task, lease and state predicates. Never promote syntax-only preflight, a caller Boolean or a primitive observation directly into transaction/work/FinalUse authority.
4. **Replay and durable effect semantics.** Model the difference between reversible ledger state and irreversible local execution/release/withdrawal journals. Restart or reorg must not refund a consumed external effect. Randomized ML-DSA signatures or alternate encodings of the same signed intent must not create new operation IDs, approvals, tickets or PoN credit.
5. **Custody and recovery.** The adapter receives an already-owned PKey. Real node/operator deployment still needs key-generation custody, canonical persistence or external signer integration, rotation/revocation, backup/recovery, policy enforcement and explicit authorization of every signed intent. No HSM or side-channel qualification follows from this adapter.
6. **Resource and transport requalification.** Measure real ML-DSA verification/signing, 3,309-byte signatures, 1,974-byte DER keys and large-payload commitment hashing under the actual same-Host CPU and byte ledgers. Recheck early rejection, parsing limits, cookies, batching/cache bindings and duplicate/replay pressure. Existing Ed25519 timings are not evidence for PQ admission budgets.
7. **Version activation and downgrade negatives.** Tests must cover mixed generations, stale revoked keys, old/new wire confusion, omitted role signatures, forged context, restart/reorg replay, malformed DER, valid signature under wrong owner, old Ed25519 fallback and real cryptographic failure. Feature compilation alone is not a consensus or deployment activation.
8. **Keep whole-chain PQ separate.** Signature migration does not resolve quantum PoN search, DAA/fork-choice credit under quantum resource models, reversible-oracle implementation costs, STARK/Fiat–Shamir/QROM parameterization, confidentiality, DA availability or actual Hepta use. The pure-PoN 2C arithmetic models remain research NO_GO evidence, not a QPU attack or a theorem of resistance.
