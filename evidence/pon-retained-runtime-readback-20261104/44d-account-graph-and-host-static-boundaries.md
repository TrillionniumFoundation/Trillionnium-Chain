# Static boundaries for account-graph reuse and Host checkpoints

This is a source review of commit `44d3def32f515b98fc41f074fe1b88e97f046191` (tree `f3e07fc21a74e9a4367610ba10f5883213609320`). The Host file was also read at `a10c39025cdc03d3265b031d6547b11e0350da2c`, where its blob remains `7089e961965af9209f2d588061c8526c5acba161`. This note records existing invariants and concrete counterexamples. It does not report a new native execution, benchmark, source change or acceptance result.

## Account-graph reuse

The current scope supports reuse only after the last write in the original main WRITE transaction. `publish_with_readback` verifies the parent before `native_store::apply` and the record save, then creates `PostWriteReadback` and verifies the child. The constructor normalizes SQLite's parsed schema and prepared statements with the original `PRAGMA writable_schema=RESET` before capturing its new no-write baseline. Subsequent uses still read current SQL State/records/deltas and perform the complete-State comparison. Only four nominated record roles can use the account-graph result; nomination alone supplies no proof. Any potentially writing SQL disables the scope, and a mutation after a consumed hit causes rejection. [Publication source][publication] [Readback owner][owner]

A parent frontier produced before that RESET cannot currently be carried through even an apparently append-only write sequence. The existing `trusted_reset_exposes_preexisting_catalog_and_prepared_vm_divergence` control changes the catalog's `archive_nodes` rootpage while the ordinary schema-description check and the old unscoped graph verifier still succeed. After the original RESET, the scoped verifier requires owner stop and retains no graph or hit. Thus a catalog match, SQL string, statement identity, write count or unchanged logical State does not establish that the pre-RESET parent and post-RESET child were read from the same actual table mapping. Counting an allowed number of inserts would not close this gap. This is a source-level reading of the original control, not a newly executed test. [Original RESET control][reset-test]

`TransactionScope` tracks attempted statement execution, including potentially writing no-row/failed statements and transaction-control ABA. Its own contract excludes prepare-time PRAGMA effects and other indirect mutation mechanisms from a general immutability certificate. It does not issue a typed certificate that particular statements changed only newly inserted nodes. Callback writes, trigger effects, replacement/deletion behavior, DDL and schema ABA therefore cannot be waived as equivalent to a trusted append merely because a statement or row counter has an expected value. The existing foreign-writer control also shows that a foreign connection blocked during the original WRITE transaction can corrupt an account node after COMMIT, and the next ordinary read must detect it. No proof crosses COMMIT, rollback, transaction replacement or reopening; `data_version` and mtime are not substitutes. [Observer contract and implementation][transaction] [Original foreign-writer control][foreign-test]

The existing frontier remains one complete-traversal result with sixteen depth-four slots. Its original test asserts at most 4 KiB. Partial results cannot become a source frontier; each actually visited node still executes its original progress callback, and exposed nodes retain their actual reads and validation. Reusing this mathematical account-subgraph evidence does not authorize skipping complete-State, nonce, record, debt or reorganization checks. The present review identifies no proven extension of that scope through the publication writes, and proposes no relaxation of the existing assertions, cancellation order or limits. [Frontier source][frontier] [Original frontier controls][frontier-tests]

## Host checkpoints

The accepted normal `KernelBudget::verify` path calls `check` once. That call freshly reads the boot ID, obtains one parent-directory metadata object, reads the actual calling thread's `/proc/thread-self/cgroup`, and reads each of the five distinct limit files in order. The file type, uid, mode, device and inode checks use that one metadata object. The seven file paths are distinct; this is a source count of opens on the successful path, not a measured syscall breakdown. Limit paths are already retained as immutable names, and the common read paths already use bounded stack buffers. No repeated fresh read of the same resource was found inside that successful check. [Kernel verification and readers][kernel]

The reader loops must reach real EOF and preserve late I/O errors. All five limit reads occur before numeric validation: the original control combines malformed `cpu.max` with missing `pids.max` and requires the later I/O error to take priority. Returning on a valid prefix or parsing each file early would change these semantics. The CPU refill path's resource checks straddle an actual CPU observation and the original waiting/deadline path; they are not adjacent duplicate reads. Existing History code already removed the earlier adjacent duplicate checks while retaining every original native progress boundary. No further read coalescing, authorization cache, checkpoint sampling or budget extension is justified by this review. [Original reader controls][kernel-tests] [CPU refill order][cpu] [History checkpoint wiring][history]

The [frozen 44d Host readback](44d-host-readback-success.json) and [native cost readback](44d-native-cost-and-confirmation-readback.json) retain different, potentially nested clock scopes. Host CPU includes each actual invoking thread; caller CPU has its original narrower scope. Their values cannot be subtracted or divided to infer an exclusive fraction. Neither report splits fresh I/O from parsing or attributes the aggregate to an individual syscall. Unknown History observations and an empty History array remain outside complete cost totals.
