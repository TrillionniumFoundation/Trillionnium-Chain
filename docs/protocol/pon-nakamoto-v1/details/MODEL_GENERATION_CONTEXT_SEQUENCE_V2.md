# Context-bound generation sequence V2

This is an explicit offline composition of the existing model evidence owners,
not a trainer, a second journal, an installer or a production acceptance grant.
The sole development plan remains the repository development plan.

## Relation

`verify_context_bound_generation_sequence` in
`formal/pon-nakamoto-v1/model_generation_sequence.py` first executes the complete
V1 sequence verifier and the context-bound signed V2 consumer verifier. Both must
name the same verified signed decisions. Each supplied complete run plan must
project to exactly the task IDs, prompt hashes, source groups and partitions
retained by its exposure-history row. A mismatch is rejected with
`GENERATION_SEQUENCE_EXPOSURE_BINDING`.

This closes a composition/import consistency gap: independent acceptance of plan
identity and signed context alone does not compare actual plan exposure with the
history declaration. An internally rehashed and re-signed package may otherwise
state fresh history while the supplied plan repeats a previously evaluated prompt.
The normal exposure admission already projects plans. This additional check does
not break a trusted external history pin or replace its durable owner.

## Namespace and boundaries

The original V1 file prefix, result bytes and callers remain unchanged. The new
result uses schema `pon-model-context-bound-generation-sequence-v2` and domain
`model-context-bound-generation-sequence-v2`. The caller supplies the initial
model and expected history from its existing admitted owner and keeps Python
inputs immutable for the call. No result is emitted until every gate passes.

All existing installation, independence, hidden-window, custody, prospective,
reward and production flags remain false. Dual signatures demonstrate key
possession, not separate administrative control. A valid no-gain decision or a
positive-gain safety/consent/resource hold remains a legitimate `no_update`.
Actual predecessor installation, newly authorized untouched future tasks,
independent adoption and withdrawal remain separate runtime obligations.

## Regression contract

`formal/pon-nakamoto-v1/test_model_generation_sequence_context.py` has eight
synthetic signed test methods. They cover all six context role signatures,
rehashed assessment substitution, all four exposure fields, concealed actual
prompt reuse, missing contexts, lawful holds and original identity/time guards.
The negative fixtures rehash and re-sign consistently so semantic rejection is
not confused with superficial signature failure.

The earlier local delivery ran these against an explicitly isolated dependency
slice with synthetic network parameters. That is not full integration evidence.
This remote continuation must run the actual repository modules and pinned
requirements on x64/ARM64, exact head and actual main merge, and pair the same
new Chain source with the existing sealed Hepta owner. No historical pass transfers.

## Five-priority continuation boundary

The original pressure budgets, attack envelope, work relation, state cap, complete
state assertions, 4105-block history campaign and full-capacity tests are retained.
A finite successful run without observed budget depletion is not saturation
fairness. Physical power loss, long-term availability, independently administered
WAN operation and genuine model generations cannot be supplied by this document.

Local Git transport and the attempted original preflight returned exit 128 in the
editing environment; no complete local checkout, native build or preflight pass
is claimed. Hosted checks on the actual committed source remain mandatory. No
main merge, force push, protection bypass or production activation is requested.

## Explicit parent-control successor V3

`verify_parent_bound_generation_sequence` in the same existing source owner
executes all V2 checks and additionally binds each plan's `current-backbone`
control artifact to that generation's `predecessor_model`. V2 permits a correctly
rehashed and re-signed plan with a different control; its historical contract and
results remain unchanged. V3 does not credit such a plan as a parent comparison.
The result has schema `pon-model-parent-bound-generation-sequence-v3` and hash
domain `model-parent-bound-generation-sequence-v3`; no chain revision changes.

For this stricter gate, current-backbone means the already adopted snapshot run
without additional control training. It is not a cast of the immutable family
backbone root into a model-release identity. Initial selection remains externally
pinned; later predecessors follow actual reported adoption or no-update decisions.
An equal artifact in another control slot is insufficient. No silent fallback to
V2 is permitted when a caller expressly requests V3.

The ten tests in `test_model_generation_sequence_parent.py` use the existing
actual Ed25519, context and exposure owners. They retain all eight possible
adopt/no-update sequences, five no-gain/owner-hold reasons, and negatives for each
substituted or stale parent, the wrong control slot, changed plan contexts, every
receipt/context role signature, chronology and hidden exposure. V2-positive,
V3-negative controls distinguish the new semantic check from signature failure.

`.github/workflows/pon-model-parent-acceptance.yml` adds bounded x64/ARM64 head and
actual-main-merge runs of the original window/context/sequence suites and all ten
new tests. It retains failures, rechecks source, and exports the exact reference
sources and logs. It replaces no original workflow, selector, budget or capacity
campaign. Hepta's exact native pair must execute the same new tests on the same
pinned Chain tuple, in addition to its existing signed-model/native boundaries.

This closes a supplied-evidence parent-comparison binding, not an end-to-end
learning experiment. It cannot authenticate actual execution, install models,
withdraw consent, infer independent operation, price physical work, or establish
WAN TPS, permanent state growth or physical power-loss recovery. Existing false
acceptance flags remain inherited without promotion. Local syntax/source-prefix
checks are separate from the required committed-source executions.
