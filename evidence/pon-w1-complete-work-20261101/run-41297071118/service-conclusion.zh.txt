具体实现定位及可证明边界

1. public_v3_from_zero.rs:1277 的 signed_confirmation_phase_with_builder 先串行提交七块，再在同一个绝对截止时间内调用 receive_public_page_from_before。压力下提交阶段已消耗 1.56–2.56 秒。随后 History 导入报 PUBLIC_REQUEST_DEADLINE；本地没有得到窗口后的排空或补成功信用。

2. history_import.rs admit_packet 里的每个 W1 callback 都执行 history_checkpoint(..., &|| control.check())；scalar_cpu.rs:685 的 observe_with_control 在 CPU observation 前调用 resource，并在每次补额等待继续调用。control.check 会做实际 Host 核验。这是当前“每 native boundary 资源/撤销检查”的明确合同，不能将 1099 个检查本身称作 bug 或直接删掉。

3. 同一 callback 后面还运行 history_kernel_work_checkpoint(point) 的稀疏分支，触发第二次 Host 核验。对保留的七个真实合法 proof 重算 noise 扩展，没有拒采样，每个 proof 为 1099 个 callback + 30 个额外稀疏核验，共至少 1129 次 Host 检查；每次读取 boot ID、实际线程 cgroup、五项 limits，并核对父组元数据。ingress.rs 的“每64 tiles” helper 单测只数 predicate，不计这条整合调用路径。因此存在可精确定位的成本位置，但没有实际独立 History 分阶段 CPU 或 syscall trace，不能宣称它独自解释了全部失败，也不能仅依据稀疏 helper 改变既有 guard 合同。

4. 两个 fixture 都使用 PublicServer::new，arithmetic_facts=None、w1_rejection_cache=None。接收方 Submit 经 public_v3.rs:1564–1571、store.rs:624 到 pon_work::verify_with_progress；独立 History 经 history_import.rs:240 同样到默认验证器。切换默认 FullLimb 会作用于这两条实际路径。ArithmeticFactCache 固定 Transposed 不参与本组；生产者 PreparedTask 也不因默认验证核切换而改变。

建议的下一项判别性工作

先独立切换 FullLimb 默认核，保持原 4 秒/16 worker/0.25 CPU 和全部 guard 语义，保留新的正负收据。若仍失败，再在同一预算下为独立 History 分别测量 decode、W1、Host核验、M06、activation、SQLite commit；对实际 resource callback 数做集成计数并覆盖撤销/取消/补额测试。可以优化保持全部物理读与失败顺序的实现成本；不能把删 guard 或扩大预算包装成修复。

当前无法从这些 artifact 证明一个确定的实现逻辑 bug。已证明的是：原始服务门槛真实失败；接收方拒绝与记账正确；公共页独立验证推进不足；固定 Host 的资源竞争与具体 History 检查路径值得下一步测量。该结论不关闭工作硬度、安全经济性或公网资源公平验收。
