# trnm-service-settlement

Owner: M12. Reusable candidate component; no consensus activation.

Bilateral usage/escrow conservation; no consumption-derived voting power.

Domains and data schemas use a fresh portability namespace. Never open a deployed
historical database as an upgrade shortcut. Retained tests cover local behavior only.

This is a local monotonic commit/replay kernel, NOT a branch-reorganization backend.
PoN authoritative integration requires a new branch/undo adapter and crash qualification.

```bash
cargo test --locked -p trnm-service-settlement --all-targets --all-features
```

Run from `trillionnium`. See [modules](../../../docs/modules/README.md) and
[ownership](../../../config/portability-inventory-v1.json).

Price tables and receipt usage require unique resource keys
`(resource_class, resource_id, meter_id, meter_version, unit)` as well as the
existing full-record canonical ordering. Different prices, amounts, or measurement
commitments do not make duplicate resource keys distinct. This validation changes
no serialized fields, canonical bytes, signed domains, or stored schema; valid
unique-key inputs retain their existing encodings. Previously accepted ambiguous
configurations or receipt histories fail validation on open/replay and are not
silently migrated.

Protocol fees use the exact integer floor of `charge * numerator / denominator`
for every validated `u128` ratio (`denominator > 0`, `numerator <= denominator`).
A checked-product fast path and a bounded 128-step quotient/remainder fallback
avoid rejecting a representable fee solely because its intermediate product
exceeds `u128`. For example, `MAX/MAX` now settles identically to `1/1`.
Destination balance overflow still rejects atomically. This changes no rate,
asset, encoded policy fields, signed bytes/domains, or stored schema. Existing
successful histories retain their results; previously rejected valid ratios can
now settle. No stored histories are rewritten; this remains a portable local
candidate, not consensus activation. Tests include full-width escrow conservation
and cold replay, plus
independent Python-bigint vectors regenerated by
`python3 test-vectors/generate_fee_vectors.py` from this package directory.

A recorded empty successor block cannot later acquire its first command. Such an
input is rejected within the transaction without changing the durable head;
valid first commands at the self-parent genesis anchor and additional commands
in a nonempty current block remain supported. An existing store handle also
cannot issue a fresh confirmation carrier after the store is permanently fenced.
Previously malformed journals remain rejected on audit/reopen; there is no
migration, journal repair, or change to stored schemas or signed domains.

Read-only opens use SQLite locking and a deferred transaction rather than claiming
that this mutable file is immutable. Each audit and its returned head, state or
receipt use one read snapshot; preview state and duplicate checks share that
snapshot. Write-side audits run inside the immediate write transaction. A proof
carrier records a historical observation, not revocable current authority.

Only rollback-journal database format is supported. Existing sidecars and WAL
header format are rejected before SQLite read-only open, so a closed WAL database
is not opened merely to create new WAL/shared-memory files. No journal-mode
setting is changed or automatic recovery attempted. Concurrent external pathname
replacement or journal-mode mutation is outside this ownership contract; header
admission is not an atomic exclusion mechanism for such external changes.

Read-only execution previews enforce the durable SQLite signed-integer range for
both candidate height and projected final operation sequence, including empty
batches. A preview rejects an unrepresentable target before processing commands;
this changes no persisted schema or signed domain. Boundary tests exercise real
stores at the last representable height, rejection with unchanged database bytes
and cold-reopen state, and preview/commit parity. Sequence exhaustion is checked
with synthetic helper inputs, not a practically constructed maximum-length history.

New rollup admission, in both preview and execution, also requires a strictly
later settlement height that fits SQLite's signed-integer range. The check runs
after ordinary transition validation, preserving signature and input errors.
Historical audit and exact operation replay retain their existing semantics:
previously accepted unfinishable rollups remain readable and are not repaired.
There is no rollback, migration, stored-byte rewrite, schema/domain change, or
change to the configured challenge duration. This admission guard only prevents
new rollups whose earliest settlement height exceeds backend capacity.
A test-only persisted legacy journal covers challenge-close heights `i64::MAX`,
`i64::MAX + 1`, and `u64::MAX`: cold audit/readback and exact operation retry
preserve the original receipt, state, head and database bytes. The same inputs
are rejected as new rollups. Historical readability does not make those rollups
settleable or repair their maturity bounds.

Fresh store creation checks that the initial Order height fits SQLite's signed
integer range before creating a directory or database. An out-of-range height
leaves a missing path untouched, allowing a corrected configuration to retry.
The maximum representable height remains supported. Existing-store audit,
stored schemas and signed domains are unchanged; no caller files are removed.

Empty-block retries authenticate the recorded parent and require an empty
successor marker in the same read snapshot as the returned head. A matching
target alone does not acknowledge a changed parent, a nonempty block, or the
self-parent genesis anchor. These conflicting retries return `Conflict` without
changing durable bytes. Exact empty retries remain supported, including after
cold reopen; stored schemas and signed domains are unchanged.

Read-only previews reject candidate block IDs already recorded anywhere in the
committed-block journal, including the genesis anchor. The check shares the
audited source snapshot and applies to empty and nonempty candidates, matching
the durable backend's existing uniqueness constraint. Historical audit, exact
operation retries, stored schemas and signed domains are unchanged.

Local process-death tests explicitly launch an ignored child-test fixture and
terminate only that owned child at two signaled stages. Death after transactional
writes but before COMMIT preserves the database and rollback journal while public
store operations fail closed with `SidecarPresent`; no recovery is attempted.
Death after COMMIT and connection close, before acknowledgment, permits cold audit
and exact retry of the single durable operation. This does not add automatic
recovery or qualify power loss, torn writes, or arbitrary crash points. The ignored
fixture is exercised by the ordinary parent test rather than run independently.

A controlled two-handle concurrency test releases both writers only after their
read-only preflight snapshots close. Exact duplicate operations serialize to one
commit and one replay; distinct operations proposing incompatible successors
serialize to one commit and one stale-parent rejection. Cold audit, exact retries,
and the single durable operation are checked. The rendezvous is test-only and
time-bounded. This qualifies that schedule, not arbitrary concurrent entry,
process death, power loss, or an authoritative chain integration.

New successor-block admission rejects an all-zero block ID in both empty advances
and command execution, matching the existing read-only preview rule. Rejection
leaves the head, state and database bytes unchanged, so a corrected nonzero target
can be retried. This admission-only check does not rewrite historical zero-ID
markers or change cold audit, exact retry, or genesis/same-block semantics. Tests
retain canonical historical empty and nonempty zero-ID successors and a zero-ID
genesis anchor. Stored schemas and signed domains are unchanged.

Read-only SQLite URI construction escapes the second slash of a leading `//`
pathname instead of allowing it to be parsed as a URI authority. The decoded
pathname bytes, read-only flags, locking, sidecar checks and schema are unchanged.
Linux tests cover ordinary, double- and triple-leading-slash paths with reserved
characters, UTF-8 and non-UTF-8 filename bytes through creation, preview, execution
and cold exact replay. These pathname tests do not qualify Windows UNC semantics
or external pathname replacement.
