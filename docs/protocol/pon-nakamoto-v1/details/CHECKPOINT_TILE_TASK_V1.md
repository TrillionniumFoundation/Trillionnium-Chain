# Mandatory checkpoint tile maintenance development profile

This explicit revision 10 candidate installs `signed-checkpoint-tile-maintenance-dev-v1` with `native-operator-checkpoint-tile-dev-v1`. It requires the complete original material replay described in [CHECKPOINT_TILE_MATERIAL_V1.md](CHECKPOINT_TILE_MATERIAL_V1.md). Existing V1–V4 task profiles, QWT1/QDL2/PNW1 bytes, historical genesis values and their evidence remain unchanged. Selecting the new task name through the ordinary development constructor fails; the explicit operator material constructor is required.

`CheckpointTilePolicySpecV1` is a bounded, canonical context-free policy. It commits the exact verifier policy, complete checkpoint SHA-256 and size, activation SHA-256, canonical 16 KiB A/B SHA-256, their existing artifact identities, and matrix task identity. It contains no network or parameter identifier. The outer operator specification embeds this policy and the unchanged V1 actor roster/funding specification; the inner V4 name describes the reused lease codec, not the effective revision. New registry hashes, the outer specification and policy are committed before deriving the fresh network and parameter identifiers. `Config::installed_with_checkpoint_tile_policy` validates the bounded policy and computes context commitments; it does not read or replay original files. The final verifier descriptor is derived afterward. The requester approval commits its identity, final network/parameters, lease, manifest, and descriptor identity; this ordering has no circular hash dependency.

`Settings::development_with_operator_checkpoint_tile` and every `Node::open`, including reopening a stored database, replay the complete checkpoint stream, bounded activation and each matrix's 4,096 A/B words (8,192 words in total) using explicitly pinned originals. The strict original SHA, whole-file size, safetensors header/offsets, exact integer IEEE quantization, activation schema, coordinates, padding, exact matrix bytes and task identity checks are mandatory. The material replay does not certify an external expected C; the later native PNW1 verifier still checks the complete product/transcript relation. The Unix file adapter rejects symlinks, nonregular files, multiple hard links and group/other writable inputs; it compares checkpoint descriptor metadata before and after replay. The full stream hash still establishes the bytes read, not a claim that arbitrary files are immutable. Replay is bounded to 512 MiB checkpoint, 1 MiB activation, 32 KiB policy/operator specification and 90 seconds of cooperative replay observation. It is not preemption inside file I/O, a process RSS cap or a guarantee against malicious storage latency. A failed replay occurs before creating the Node store directory, owner lock or SQLite database.

The source signs the exact QWA2 source statement carrying the original QWT1 maintenance manifest in the fresh context; QDL2 encodes its demand lease. The requester signs a distinct `operator-checkpoint-genesis-requester-v1` approval. Offline signing replays all public inputs and compares the entire template before opening an explicit effective-UID-owned mode-0600 signer file, then requires its actual public key pin. No Node path creates or substitutes DEV actor signatures. Known DEV16 exclusion remains the existing narrow exclusion and does not certify arbitrary operator key generation or custody. Old actor templates, approvals, bundles, stored namespaces and new ones are mutually refused.

Only maintenance leases with cost class 1 and output limit 0 are allowed. Every source registration and actual parent eligibility check must match the installed A/B/model/input/task/layer/recipe relation. Tags 18/20/21 retain open/revoke/register semantics; tag 22 retains the V4 atomic renewal and source registration with its overlap window, source sequence, output meter and count. Standalone tag 19 remains refused. A valid material replay does not override lease activity, source signature/window/sequence, withdrawal, availability, actual parent State/root, transaction nonce/fee, receipt, fork or SQL rules. Successor output consumption is still checked against the actual executed successor State. Renewing a lease requires explicit requester and source signatures and retains the installed material; selecting another original checkpoint requires another fresh deployment context. There is no cross-operation authority cache.

The CLI keeps the existing `genesis-prepare`, `genesis-sign`, `genesis-finalize` and Node commands. Use the explicit new actor profile, new canonical `--deployment-spec`, `--deployment-model`, `--deployment-input`, `--deployment-checkpoint`, `--deployment-activation`, and, for Node commands, `--deployment-bootstrap`. The original actor profile rejects the new original-file options. An explicit miner remains required for `make`, `mine`, `mine-loop` and `serve --mine`. Registered-material continuous mining reads the current actual parent source statement; `--task-bootstrap` denotes the signed initial maintenance statement and cannot silently renew it.

This contract checks exact material provenance and the finite quantization relation for the fixed layer-0 q_proj tile. The existing QWT1 `layer` and `recipe` fields still identify the 64-material contract; they are not reinterpreted as a complete checkpoint coordinate or full forward pass certificate. The original source-record and demand semantics are unchanged. Activation origin is a bounded source-attested record, not an independently verified model execution. Cost class 1 labels the declared fixed logical relation; it is not a measured minimum miner cost. Padding, sparsity, low rank, preprocessing reuse and task selection remain material cost-class concerns; this profile deliberately permits them as maintenance with no useful-output credit. It does not establish genuine user demand, mining hardness, marginal contribution, globally optimal circuits, objective model quality, independent operation, WAN fairness, indefinite service or public release qualification. All corresponding acceptance flags are false.

The new ordinary tests use disclosed deterministic test keys and synthetic numeric/parser inputs. A separate explicitly selected ignored control replays the existing pinned Stage A original file/activation/A/B and then makes, fully admits, activates and reopens an actual native maintenance block. Neither synthetic controls nor the Stage A test prove independent full-forward execution, valuable output or production governance. Execution receipts are external until separately published; old evidence must not be relabelled as a revision 10 run.
