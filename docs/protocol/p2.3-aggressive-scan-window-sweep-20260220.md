# P2.3 Aggressive Scan Window Sweep (2026-02-20)

## Setup
- Command output CSV: `trillionnium/run/bench/aggressive-scan-window-sweep-20260220-143130.csv`
- Workloads:
  - `mixed` (`txs=10000 keys=2000 read_fanout=4 write_every=2`)
  - `hot-streak` (`txs=10000 keys=256 read_fanout=4 write_every=1`)
- Strategy compared:
  - baseline `original`
  - `aggressive-greedy` with `TRNM_AGGR_SCAN_WINDOW in {0,2,4,8,16,32}`

## Result Summary
- Baseline:
  - mixed/original = **22ms**
  - hot-streak/original = **26ms**
- Aggressive best observed:
  - mixed/aggressive = **49ms** (window=0)
  - hot-streak/aggressive = **56ms** (window=2)
- Window sensitivity:
  - very small; elapsed + groups almost unchanged across tested windows.

## Conclusion
`TRNM_AGGR_SCAN_WINDOW` is **not a high-leverage knob** in current aggressive implementation for these representative cases.

## Decision
- Keep aggressive as experimental and non-default.
- Do not prioritize scan-window tuning for next round.
- Next hypotheses should focus on:
  1. reducing aggressive bookkeeping overhead (hashset intersect cost / memory churn), or
  2. reducing unnecessary candidate checks through stronger lower-bound/index hints.
