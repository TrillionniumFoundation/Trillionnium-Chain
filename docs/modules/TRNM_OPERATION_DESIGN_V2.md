# Operation-level implementation contracts v2

Status: **candidate design expansion, not semantic acceptance or production activation**.
Primary owner M17; each row's M00–M17 prefix identifies its semantic owner.

This is a technical contract supplement, not a second roadmap. The existing
`config/documentation-operations-v1.json` and
`config/documentation-operations-supplement-v1.json` retain their exact executable
source/test bindings. These tables add explicit operations outside that small
foundation inventory. They do not rewrite frozen v0 bytes or supersede an
operation's more specific versioned module specification.

Each module's existing `Mxx_*_TECHNICAL_SPEC_V1.md` supplies exact field layouts,
error enums, profile constants and referenced source symbols. `Existing`,
`candidate` and `target` in the entry column distinguish source reuse from a
required new adapter; a target is not reported as implemented. A number called
"proposed" is only the already documented development profile, not a mainnet
parameter. New economic behavior is further constrained by
`docs/security/POCO_ECONOMIC_SECURITY_CONTRACT_V1.md`.

## Coverage semantics

The checker reports three separate things: detailed rows in this supplement,
source/test records in the existing catalogs, and unclassified public source
declarations in registered crates. The default check keeps this last count unknown;
`python3 scripts/ci/check_operation_design_v2.py --scan-public --output /tmp/operation-inventory.json`
runs the bounded declaration audit explicitly, without adding a whole-source scan
to every small documentation change. A public helper is not automatically a
product operation; it still needs classification before a complete surface can
be claimed. The lexical inventory includes conditional and test declarations
and does not establish Cargo feature reachability or macro expansion coverage.
No row count, complete module list, or empty lexical difference is an independent
semantic review. **Whole-project operation completeness remains unproved.**

The columns are implementation obligations: authenticate the named input,
perform the ordered effects, preserve the named durable/retry invariant, bound
resources and distinguish failure, then exercise the concrete acceptance case.
Every mutable operation additionally needs actual producer/consumer testing at
each durable boundary. Missing independent bytes or physical fault evidence
remain missing; the checker never fabricates those results.
