# 05 — PoCO Weights, Bond, and Accountability

## 1. Purpose and non-claims

PoCO-BFT derives an epoch candidate's raw voting capacity from two independent ceilings:

1. matured, decayed, relationship-capped Consumption Certificate units;
2. active slashable bond.

The smaller ceiling wins. This prevents certificate volume from creating voting power that is not also bond-backed. It does not prove that consumption was socially useful, competitively priced, non-collusive, or generated by independent parties.

The numeric values in `parameters.toml` are a **P0 reference shadow profile**, not audited mainnet economics. The profile sets `production_activation = false` and MUST NOT be interpreted as authorization to activate economic consensus weight.

## 2. Arithmetic rules

Every intermediate sum, multiplication, subtraction, comparison, cap, and conversion in this document uses checked unsigned `u128` arithmetic. Division is integer floor division. Negative values, floating point, decimal strings, saturating arithmetic, wraparound, implementation-native `usize`, and nondeterministic iteration are forbidden.

If any candidate calculation overflows, references malformed state, or violates a bound, the complete next-set candidate is invalid and the deterministic current-set fallback rule applies. Implementations MUST NOT skip only the offending validator and continue unless a future protocol version explicitly specifies that behavior.

After all checks, each effective weight MUST fit `u64` and the configured maximums.

## 3. Eligible Consumption Certificates

For the snapshot in epoch `s` that constructs epoch `s + 1`, a Consumption Certificate contributes only if it:

- conforms to `poco-consumption-certificate-v0` and has a valid certificate ID/signature;
- was accepted and finalized no later than the exact snapshot cutoff state;
- is not duplicated, revoked, successfully challenged, or already invalidated;
- maps its provider identity to exactly one registered candidate validator;
- uses a recognized meter/version and an eligible relationship classification;
- has `consumed_units > 0` and all bounded fields valid;
- satisfies maturity and age rules below.

Certificate finalization epoch is the epoch of the finalized acceptance block, not a submitter-provided wall-clock field. A certificate may affect no earlier snapshot.

Until related-party and reciprocal-consumption policy is frozen, a relationship classified as related or unresolved contributes zero units. Privacy-preserving proofs and cross-identity sybil policy remain `UNDECIDED` and block mainnet economic activation.

## 4. Maturity and linear decay

Let `f_c` be the certificate finalization epoch and `s` the snapshot epoch. A certificate is mature only if:

```text
s >= f_c + maturity_epochs
```

For a mature certificate:

```text
age_c = s - f_c - maturity_epochs
```

If `age_c >= max_certificate_age_epochs`, its contribution is zero. Otherwise:

```text
decay_ppm(age_c) =
    max(0, scale_ppm - age_c * decay_step_ppm_per_epoch)
```

Its decayed, per-certificate-capped units are:

```text
d_c = floor(
    min(consumed_units_c, per_certificate_unit_cap)
    * decay_ppm(age_c)
    / scale_ppm
)
```

The reference profile uses `scale_ppm = 1_000_000`, two maturity epochs, a 20-epoch maximum age, and `50_000` ppm decay per age epoch.

## 5. Order-independent relationship caps

For provider validator `i`, task `t`, and consumer `c`, sum all distinct eligible certificate contributions in canonical certificate-ID order. The mathematical result MUST be independent of storage or iteration order:

```text
x(i,t,c) = sum d_cert for (i,t,c)
a(i,t,c) = min(x(i,t,c), per_consumer_provider_epoch_unit_cap)

y(i,t) = sum over consumers c of a(i,t,c)
b(i,t) = min(y(i,t), per_task_provider_epoch_unit_cap)

z(i) = sum over tasks t of b(i,t)
U_i = min(z(i), per_provider_epoch_unit_cap)
```

Consumer IDs and task IDs are raw canonical bytes and group by exact byte equality. Certificate IDs MUST be globally unique in the snapshot input. Duplicate IDs invalidate the candidate snapshot rather than contributing twice.

The caps deliberately apply after aggregation at each relationship level; a submitter cannot evade them by splitting one workload into more certificates.

## 6. Raw capacity and bond ceiling

For candidate validator `i`:

```text
poco_capacity_i = floor(U_i / units_per_power)

bond_capacity_i = floor(
    active_slashable_bond_i / bond_atomic_units_per_power
)

raw_i = min(
    poco_capacity_i,
    bond_capacity_i,
    max_validator_power
)
```

The validator is candidate-eligible only if `raw_i >= min_validator_power`, its key proof is valid, it is not jailed, and all registration rules pass.

`active_slashable_bond_i` is the bond amount committed in the snapshot that remains slashable through the entire target epoch and evidence window. Pending deposits that are not active and unbonded or withdrawable amounts do not count.

Because effective weight never exceeds `raw_i`, every active weight unit is backed by at least `bond_atomic_units_per_power` slashable atomic units. Implementations MUST reserve that backing against early withdrawal.

## 7. Candidate selection bound

If more than `max_validators` candidates are eligible, select exactly `max_validators` by:

1. descending `raw_i`;
2. ascending raw `validator_id` bytes as the tie-break.

After selection, encode the validator set in canonical ascending validator-ID order. If fewer than `min_validators` are eligible, candidate construction fails and carries the current set.

## 8. Rollout phases and effective weight

The active rollout phase is a finalized, epoch-committed parameter.

### 8.1 `shadow`

Compute and commit diagnostics for `U_i`, `raw_i`, candidate membership, cap hits, concentration, and fallback status. The active next epoch carries the existing/genesis membership and weights. Shadow calculations MUST NOT affect consensus validity, leader selection, rewards, jail, or slashing.

### 8.2 `eligibility-only`

PoCO/bond determines candidate membership. Every selected validator receives:

```text
w_i = 1
```

### 8.3 `capped-weight`

With `alpha_ppm = capped_weight_alpha_ppm`:

```text
w_i = 1 + floor(alpha_ppm * (raw_i - 1) / scale_ppm)
```

### 8.4 `full`

With `alpha_ppm = full_weight_alpha_ppm = scale_ppm`, the same formula yields:

```text
w_i = raw_i
```

No phase promotion is automatic. Promotion requires a finalized governance decision, satisfaction of the minimum observation epochs in the active parameters, and activation at a joint epoch handoff. Governance MAY schedule a demotion to a more conservative phase, also only at an epoch boundary. A node using the reference profile with `production_activation = false` MUST reject a commitment that attempts to leave `shadow`.

## 9. Validator-set validity

After effective weights are assigned, let:

```text
W = sum w_i
M = max w_i
N = number of validators
```

The candidate is valid only if all of the following hold:

```text
min_validators <= N <= max_validators
0 < W <= max_total_voting_power
3 * M < W
M * scale_ppm <= max_validator_share_ppm * W
```

Every multiplication is checked `u128`. IDs and consensus keys are unique and every weight is positive. The reference `max_validator_share_ppm = 250_000` caps a validator at 25% of total effective weight.

These structural constraints limit single-validator concentration but do not establish independence between validators or operators.

## 10. Bond, unbond, and jail timing

A bond activation, unbond request, withdrawal, jail, or release is an application state transition that affects consensus weights only at a later snapshot.

An unbond request MUST remain slashable for at least `unbonding_delay_epochs`. The configured delay MUST be greater than or equal to the objective evidence window and greater than the light-client trusting period. Withdrawal before all active epochs and applicable evidence windows have elapsed is invalid.

A jailed validator remains in the immutable current epoch set with its committed weight; removing or zeroing it mid-epoch would create inconsistent quorum denominators. It stops signing by policy and becomes ineligible at the next snapshot. This may reduce liveness but preserves one denominator.

The reference jail duration is a testing parameter, not audited mainnet policy.

## 11. Objective evidence and idempotence

`DoubleVoteEvidence` is verified exactly as specified in the consensus document. Its evidence ID is:

```text
Digest(
  "trnm.poco-bft.double-sign-evidence.v0",
  normalized_conflicting_signed_values
)
```

The two signed values are ordered by digest, so submission order cannot change the evidence ID. Evidence processing MUST:

- re-verify both signatures and their validator-set membership;
- prove identical signing identity fields and different block IDs;
- reject identical signatures/messages as non-conflicting;
- enforce `current_epoch <= offense_epoch + evidence_window_epochs`;
- record the evidence ID before applying disposition;
- apply any jail/slash/reward effect at most once.

The exact mainnet double-sign slash fraction, reporter reward, correlated-fault multiplier, downtime penalty, and non-vote penalties are `UNDECIDED`. Production activation of bond-derived power MUST remain disabled until those values and their governance/recovery semantics are frozen and audited.

Objective evidence validity is separate from economic disposition. Nodes must agree that evidence is valid even in `shadow`; the reference profile need not destroy funds.

## 12. Required observability before promotion

Shadow and staged phases MUST report enough deterministic or reproducible data to evaluate:

- concentration by validator, provider, consumer, task, and operator cluster;
- certificate duplication, challenge, maturity, expiry, and cap-hit rates;
- reciprocal or cyclic consumption patterns;
- raw capacity versus bond capacity;
- candidate churn and fallback frequency;
- quorum margin under crash and partition scenarios;
- counterfactual finality under every rollout phase;
- unbond/evidence timing and worst-case slashable coverage.

Observed success is necessary but not sufficient for promotion. External economic review remains a P3/P4 requirement.

## 13. Deterministic pseudocode

```text
function next_candidate(snapshot, p):
    assert snapshot.height == p.committed_snapshot_cutoff
    totals = empty ordered map keyed by (provider_validator, task, consumer)

    for cert in certificates_sorted_by_id(snapshot):
        validate_unique_and_structural(cert)
        if not eligible(cert, snapshot):
            continue
        assert snapshot.epoch >= cert.finalized_epoch + p.maturity_epochs
        age = snapshot.epoch - cert.finalized_epoch - p.maturity_epochs
        if age >= p.max_certificate_age_epochs:
            continue
        decay_product = checked_mul(age, p.decay_step_ppm_per_epoch)
        decay = 0 if decay_product >= p.scale_ppm
                  else p.scale_ppm - decay_product
        d = min(cert.consumed_units, p.per_certificate_unit_cap)
        d = floor(d * decay / p.scale_ppm)
        checked_add(totals[key(cert)], d)

    for provider in providers_sorted_by_validator_id(totals):
        U = hierarchical_caps(provider, totals, p)
        poco = floor(U / p.units_per_power)
        bond = floor(snapshot.active_slashable_bond(provider)
                     / p.bond_atomic_units_per_power)
        raw = min(poco, bond, p.max_validator_power)
        if raw >= p.min_validator_power and registration_valid(provider):
            include(provider, raw)

    select_by_raw_then_id_if_needed()
    assign_effective_weights_for_committed_phase()
    validate_complete_set_or_fallback_atomically()
```

This pseudocode is explanatory. The equations and rejection/fallback rules above are normative.
