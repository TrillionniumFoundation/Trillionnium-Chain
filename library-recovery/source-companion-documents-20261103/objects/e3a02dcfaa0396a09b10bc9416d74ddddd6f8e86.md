## 二、运行方式

仅需 Python 3.10+ 和 Git，无第三方 Python 依赖。将本目录置于目标仓库**外部**，以避免未跟踪文件影响 clean-HEAD 检查。

```bash
# 1. 自身测试
cd trnm-pq-security-kit
python3 -m unittest discover -s tests -v

# 2. 针对真实 checkout 输出可审计报告（默认非严格模式仅做诊断，激活/资格自声明依然报错）
python3 pq_readiness.py \
  --repo /absolute/path/to/Trillionnium-Chain \
  --policy pq_evidence.template.json \
  --output pq_readiness_result.json

# 3. 严格模式：任一证据缺失即退出 2；不能把失败当成“CI 坏了”直接关闭
python3 pq_readiness.py \
  --repo /absolute/path/to/Trillionnium-Chain \
  --policy pq_evidence.template.json \
  --output pq_readiness_result.json \
  --strict

# 4. 量子难度研究的玩具模型：非 W1 专用
python3 quantum_difficulty_screen.py --difficulty-multipliers 1 4 16 256 65536
```

输出包含：`head_sha`、`clean`、六大门禁 blocker、固定热点源文件 SHA256、W1 清单原值、Ed25519/ML-DSA/Groth16 等未分类引用位置。代码引用**只是清单**；不能把未激活代码判定成漏洞，也不能把扫描没发现引用判定为安全。

报告字段 `pq128_certified` 和 `production_approved` **恒为 false**，因为静态工具无法复核零知识证明的量子 soundness、量子矿工最优下界、密钥生命周期或完整运行时路径。即使所有外部证据文件、SHA256 与“独立复现”元数据齐全，最多只能输出 `EVIDENCE_PRECHECK_PASSED_NOT_CERTIFIED`。

## 三、六项互相独立的 P0/P1 工程门禁

### G1：身份与所有权限根（P0）

从每一项产生权限的入口追踪到最终验签器、密钥根、epoch/height、nonce、共识激活策略和拒绝路径：

`account`, `transaction`, `node_ingress`, `task_source`, `evaluator`, `model_release`, `hepta_handoff`, `provider_discovery`, `protocol_upgrade`, `governance`, `recovery`。

对旧格式的要求是：标明 legacy read-only / historical verification / active authority 三种不同语义。**不存在“见到 Ed25519 字样就算生产漏洞”的规则。**

**负例验收**：经典签名有效但 PQ 无效、PQ 有效但经典无效、旧 epoch、错误 chain ID、错误对象类型、重放 nonce、伪造 evaluator/provider/upgrade、先前合法但已撤销的密钥均按预期拒绝；并检查所拒绝交易不能借 listener/恢复/重组入口复活。

### G2：W1 透明证明与 PQ-128 资格（P0）

以精确 SHA 固定 guest、ELF/image ID、journal、receipt 类型、verifier、hash commitment、FS/FRI/递归参数、链上的接受规则。禁止在 PQ 路径把 Groth16、Fake receipt、远程 oracle 或不受约束的“任何 receipt”替代为本地 W1 关系。**实际是否能关闭此门禁取决于独立研究和证明，而不是修改 JSON。**

公开的 RISC Zero 3.0 安全模型提供 RISC-V Prover 96-bit、Recursion Prover 99-bit 的估计，并指出 Groth16 层不抗量子。`3.0.6` 清单出现且目标为 PQ-128 时，本工具会明确标红，不允许将版本标签视作 128-bit 资格。

**负例验收**：把有效 receipt 中的 claim/image ID/height/previous block、边界字段各自替换，使用不对应 W1 的 Groth16/fake/remote receipt；在实际 verifier 入口严格拒绝，并测最坏无效输入成本。

### G3：PoN/W1 量子求解与累计工作（P0）

分别冻结并复现：最低成本**合法** W1 求解器、低秩/特殊矩阵/预计算/多挑战批处理、完整量子 oracle（含输入加载、可逆计算、uncompute、输出发布）、受限容错量子资源、难度重定向及链选择重组。不能拿一个 oracle 的“实现上界”冒充最优攻击的“成本下界”。

`quantum_difficulty_screen.py` 仅说明一个抽象模型：累计工作 ∝ D、理想化 Grover 查询复杂度 ∝ √D 时，工作权重/查询成本随 √D 增加。**它不证明 PoN W1 遵循这些假设。**

### G4：密钥迁移与防降级（P0）

混合过渡阶段要求**两个验签都通过（AND）**，不是“经典或 PQ 任一个成功即可”。从预量子时期就提交 PQ 所有权，并设计灾备、遗失密钥和例外处理的后量子根；激活后不能退回经典-only。切换高度、重组分支、节点重启、账户迁移、治理升级和历史证明读取必须同一套确定性共识规则。

**负例验收**：双签其中一个无效、激活窗口跨高度重组、旧状态数据库恢复经典-only、链 ID 交叉重放、只持旧经典密钥申请升级全部拒绝。

### G5：容量与拒绝服务成本（P1）

ML-DSA-65 原始公钥 1952 字节、签名 3309 字节，而 Ed25519 分别为 32 / 64 字节。测典型交易、最大交易、区块/包片、签名验算 CPU、内存峰值、广播传播、磁盘增长和无效签名预算；拒绝流程应尽早对长度、版本、权限 epoch 与存储上限做有界检查，但必须保持协议一致的判定顺序。

**负例验收**：巨型密钥/签名长度、重复无效签名、畸形编码、压缩炸弹、批量匿名请求和 p99 拒绝成本，应有实际机器性能报告而不是纸面估算。

### G6：持久化、恢复与不可回滚锚（P0）

如果整个数据库、nonce、日志和迁移记录都回退到一个内部自洽的旧快照，数据库内部检验无法独自发现该回退。建立**数据库之外不可随快照回滚**的单调锚（例如受保护计数器或独立签名见证），固定 finality 的锚定语义、恢复拒绝策略、锚本身的故障行为与可信根。

**负例验收**：先激活 PQ 并锚定已终结高度，恢复激活前完整数据库，尝试经典-only 升级/迁移/重播。必须由外部锚阻断，而不是仅依靠旧数据库中的 nonce。还应检查合法重组不会触发错误的回滚拒绝。

## 四、证据模板填写要求

`pq_evidence.template.json` **不应直接把所有 false 改为 true**。每个门禁至少包含如下可复现的外部工件，并指向同一 `expected_head_sha`：

```json
{
  "verdict": "pass",
  "author": "actual-implementation-owner",
  "reviewer": "independent-actual-reviewer",
  "independent_reproduction": true,
  "artifact": "evidence/authorization/independent-run.txt",
  "sha256": "64-character-lowercase-hex-sha256-of-artifact"
}
```

工具能检查 reviewer 与 author 名称不同、artifact 未越界且未通过符号链接、SHA256 确实匹配；**不能**验证 reviewer 的真实身份、签名权限或报告内容的真实性。后续应由另一个独立签名验证器验证 reviewer 身份并把其签名回执纳入部署控制系统。
