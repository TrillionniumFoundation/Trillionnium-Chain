# PCQ1 / PCR1: post-quantum Cell chunk retrieval (research only)

Pinned upstream dependency: `research/pq-cell-release-attestations-20261026` at `53e3e526fcffa88886665203ea86aaa0b025a636` (PR #406). This work adds one M09/M01 offline research boundary without changing `main`, W1/PNW1 consensus, chainwork, historical transaction bytes, Hepta Final-use, activation, or installed devnet limits.

`pq_cell_custody.py` defines an exact v1 PCC1 157-byte catalog (network, 48-byte release Manifest ID, generation, size, chunk width/count and SHA-384 Merkle root), PCQ1 217-byte challenge (32-byte nonce, caller, ML-DSA key identity, generation, sequence, chunk index and <=300-second TTL), PCR1 response (bounded 1MiB chunk, canonical Merkle branch, and a genuine TPQ1 purpose=5 ML-DSA-65 signature). Root is over ordered length- and position-bound chunks; odd levels duplicate their last leaf and reject alternative encodings. Caller MUST supply independently pinned exact catalog ID and release ID; attacker self-consistency is insufficient. Real public-key IDs and signature verification delegate unchanged to the existing `pq_envelope.py`.

`OfflineOneUseJournal` implements a local SQLite WAL/FULL one-record-per-challenge observer with strict schema readback and cold-open rejection of foreign DDL, triggers and weakened primary keys. Exact retry returns ALREADY_RECORDED; concurrent connections return only one FIRST_RECORD. This is NOT a chain-wide replay nullifier or reward entitlement.

Reproduce on Python 3.13+ / OpenSSL 3.5.5:

```sh
cd formal/pon-nakamoto-v1
python3 -m unittest -v test_pq_cell_custody.py
```

13 local tests passed on Python 3.13.5, OpenSSL 3.5.5. The parent `pq_envelope.py` was copied byte-for-byte from the upstream Git blob `27e40b04ac8eaa381ad4dc017f23f226f99f3f41` and verified with `git hash-object`. Cases include genuine signatures, 217 challenge-byte mutations, chunk/proof/signature substitution, full framing limits, odd-level Merkle malleability, trust-anchor substitution under the same release ID, wrong signing keys, expiry/nonce/network/generation, foreign SQLite DDL, cold reopen and eight concurrent writers. These are local results, NOT independent cryptographic or production validation.

This code still cannot establish *persistent* storage (a server may fetch a chunk after receiving the challenge), geographic redundancy, independent peer identity, ownership of the signing key, current trusted release ancestry, export permission, physical durability, storage payment, Hepta model admissibility, quantum work-factor security, or node admission. Full Chain PQ readiness stays **HOLD_NO_GO**. A production M09 owner would have to authenticate the catalog root from a chain-confirmed and Hepta-authorized release, enforce the request nonce at a trusted client, integrate full network anti-Sybil / retrieval challenge economics and durable proof, and independently qualify multi-operator WAN availability.

## v2 continuation

An additive PCA1 purpose=4 signature cryptographically binds the exact original (caller-independently-verified) PCB1 signed release frame ID, previous catalog head and the canonical PCC1 catalog. The verifier returns a diagnostic CatalogPinObservation whose digest can be supplied to PCR1 verification. PCA1 cannot validate the underlying PCB1's evaluator source, signatures or permissions on its own, and is not an installed Chain release pointer. The updated test suite runs 15 checks with genuine ML-DSA-65 signatures and source blobs `5dabec97985cebe3de8feff51089267bd8650aea` / `4a93c30e57087fb50737a13bf53d8d680676d463`.
